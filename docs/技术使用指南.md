# 技术使用指南

首次部署请先阅读仓库根目录的 README.md。本文包含较详细的 Python 接口示例；历史性能数字仅对应特定环境和样例，不代表当前完整网页链路的达标结果。

当前版本已实现 Qwen3-4B 本地推理、SQLite 多轮上下文、流式输出与手动/新消息打断（不是自然语音插话），
以及本地离线 ASR/TTS 语音问答，
并以“尊享百万”保险资料作为当前知识库接入 RAG。知识库包含
PDF、Excel 和 Markdown；当前 RAG 是“检索后生成”，不是训练或微调模型。

## 环境

复用已配置的 Conda 环境：

```bash
source "$(conda info --base)/etc/profile.d/conda.sh"
conda activate qwen3-vl
cd /path/to/InsureVoice-Agent
```

模型位于 `models/Qwen3-4B-Instruct-2507`。接口默认使用 GPU 1、BF16 和 PyTorch SDPA；可在初始化时通过 `device`、`dtype` 和 `attn_implementation` 修改。

RAG 另外使用 `sentence-transformers==5.1.2`、`faiss-cpu==1.13.2` 和系统命令
`pdftotext`。现有环境已安装 Python 依赖；如需根据文件同步环境：

```bash
conda env update --name qwen3-vl --file environment.yml
```

## 本地离线 ASR/TTS 语音问答

语音链路为：

```text
按键录音完成
  → SenseVoice ASR（CPU）
  → SQLite 上下文 + RAG + Qwen（GPU 1）
  → 正文切分
  → CosyVoice-300M-SFT（GPU 0）
  → 22.05 kHz / 16-bit / 单声道 PCM 音频流
```

ASR 继续在 `qwen3-vl` 环境中使用 `sherpa-onnx==1.13.8` 和 SenseVoice INT8，
支持中文、英文和中英混合识别。TTS 使用 CosyVoice 的预置“中文女”音色，
不做声音克隆。CosyVoice 运行在独立的 `cosyvoice` Conda 环境中，主程序通过
`127.0.0.1` 上的本机流式协议读取 PCM，不依赖云端语音服务。

默认设备分工：

- GPU 0：桌面显示 + CosyVoice TTS（约 2.8GB 显存）。
- GPU 1：Qwen3-4B 文字生成。
- CPU：SenseVoice ASR 和 RAG 检索。

模型与运行时来源：

- [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)
- [SenseVoice](https://github.com/QwenAudio/SenseVoice)
- [CosyVoice 官方代码](https://github.com/QwenAudio/CosyVoice)
- [CosyVoice-300M-SFT 官方权重](https://huggingface.co/FunAudioLLM/CosyVoice-300M-SFT)

CosyVoice 源码位于 `third_party/CosyVoice`，权重位于
`models/speech/CosyVoice-300M-SFT`。如需在新机器复现独立环境：

```bash
conda env create --file environment-cosyvoice.yml
conda activate cosyvoice
pip install --no-build-isolation openai-whisper==20231117
```

Whisper 必须在 NumPy 和兼容版 `setuptools` 已安装后再执行第二步；
这是为了兼容其旧版构建脚本。

### ASR Python 接口

```python
from speech import ASRClient

asr = ASRClient()  # 程序启动时加载一次
result = asr.transcribe(
    "question.webm",             # WAV/MP3/WebM 等 FFmpeg 可解码格式
    corrections={"Q5M": "Qwen"},  # 可选业务术语纠错
)
print(result.text)
print(result.language, result.total_ms)
```

`transcribe()` 也接受编码后的 `bytes`，或接受 NumPy 音频数组并同时传入
`sample_rate`。第一版的录音时长上限为30秒；空音频、静音、损坏文件和超长音频会明确报错。

### TTS Python 接口

```python
from speech import TTSClient

tts = TTSClient(speaker="中文女", speed=1.0, device="cuda:0")

# 原生流式块；默认只存在内存中
for chunk in tts.synthesize_stream("你好，我是本地业务助手。"):
    send_pcm_to_player(chunk.pcm16, sample_rate=chunk.sample_rate)

# 只在显式传入 output_path 时保存 WAV
tts.synthesize("你好。", output_path="hello.wav")
```

TTS 会删除 Markdown 标记、`[来源：文件，位置]`、检索分数和来源尾注，只朗读回答正文。
`Qwen`、`RAG`、`ASR` 和 `TTS` 默认转换成更自然的中文发音，可通过
`TTSClient(pronunciations={...})` 增补业务词。
英文播报在不改变页面文字的前提下，利用离线 [CMU 发音词典](https://github.com/cmusphinx/cmudict) 与大小写判断逐字母缩写和完整单词：
`AI`、`BNCT`、`PDF` 按字母读，`Hello`、`NASA` 按整词读；流式分句不从英文词中间切断。
同形词依大小写区分，例如大写 `WHO`、`IT`、`LED` 按缩写读，小写 `who`、`it`、`led` 按单词读。
已有的业务词覆盖规则（例如“尊享e生”“PLUS”）优先。缩写与同形英文词存在歧义时，
可用 `pronunciations` 显式指定播报文本；自动判断不能保证所有新品牌名或专有名词的发音。

`TTSClient` 会检查本机服务；如果未启动，就自动用 `cosyvoice` 环境加载模型。
GPU 0 默认使用端口 8766，GPU 1 使用 8767，两者不会误连。冷启动约 8 秒，
验收时的 `<2.5s` 指标以模型已预加载为前提。

### 完整语音问答

```python
from api import Qwen3Client
from context_manager import ContextManager
from rag import RAGClient, RAGRetriever
from speech import ASRClient, TTSClient
from voice_assistant import VoiceAssistant

rag = RAGClient(Qwen3Client(device="cuda:1"), RAGRetriever())
asr = ASRClient()
tts = TTSClient(speaker="中文女", device="cuda:0")
rag.qwen.warmup()
tts.warmup()  # Qwen 预热后再预热 TTS，避免 CUDA 冷内核延迟

with ContextManager(rag, db_path="data/voice_conversations.sqlite3") as context:
    session_id = context.create_session()
    voice = VoiceAssistant(context, asr, tts)

    response = voice.stream_chat(session_id, "question.wav")
    print("ASR：", response.transcript)
    with response:
        for audio_chunk in response:
            # 网页端按顺序连续播放 pcm16，不要在块之间重新初始化播放器
            send_pcm_to_frontend(
                audio_chunk.pcm16,
                sample_rate=audio_chunk.sample_rate,
            )

    print(response.text)
    print(response.metadata["voice"])
```

`VoiceAssistant` 维持约1秒建议预缓冲，首段文字最多累积约24个字即开始合成，
后续文本最多约80个字一段。首段流式交付；其余段仅在已排队音频足以覆盖估计合成耗时并留出缓冲余量时使用完整合成，否则继续流式。CosyVoice 音频块仍直接交付播放，停止按钮可清空待播队列。
页面在用户开始新一次录音时应调用
`voice.interrupt()`，它会同时停止 Qwen/TTS 并丢弃所有尚未交付的旧音频。

语音对话的 SQLite `metadata.voice` 包含 ASR 耗时、首文本耗时、首音频耗时、
TTS 合成耗时、音频时长、最小预计缓冲余量和预计缓冲耗尽次数。SQLite 只保存识别文本、
回答、来源和指标，不保存输入或输出音频。

### 命令行验收

```bash
# 识别录音、调用 RAG/Qwen，边合成边播放
python chat_voice.py question.wav --play

# 只有显式要求时才保存合成音频
python chat_voice.py question.wav --output answer.wav

# 为特定业务术语增加纠错
python chat_voice.py question.wav --correction Q5M=Qwen --play

# 可选：改变 TTS 设备（默认 cuda:0）
python chat_voice.py question.wav --tts-device cuda:1 --play
```

当前真实验收中，1.65秒的问题录音在预热后连续运行8次，从提交到首段可播放音频的
中位数为1.392秒、P95为1.469秒、最大值为1.471秒。最小预计缓冲余量为1.156秒，
8次的预计缓冲耗尽次数均为0。该指标不包含程序首次加载模型的冷启动时间。
目标验收条件为：模型预加载、单用户、录音不超过30秒时，首音频 P95 不超过2.5秒。

通过的长音频和端到端样例位于 `data/speech_samples/cosyvoice_female_long.wav`
和 `data/speech_samples/cosyvoice_rag_answer_gpu_split.wav`。

## RAG：尊享百万保险知识库

RAG 的执行链路为：PDF 按物理页、Excel 按行、Markdown 按文本提取 → 分块 → BGE 向量化后写入
FAISS → 问题检索 → 相关片段和问题一起送入 Qwen 生成回答。

资料目录由 `KNOWLEDGE_SOURCE` 配置，未设置时使用 `/home/scai/桌面/fyx/knowledge`，
索引位于 `data/rag/insurance`。系统会忽略 `__MACOSX`、`._*`、`.~*` 和 `~$*`
临时文件。资料或费率转录改变时，加载器会根据 SHA-256 拒绝旧索引，
此时需要显式重建：

```bash
python build_rag_index.py
```

默认 BGE 模型在 CPU 上做检索，不占用 GPU 1 的 Qwen 显存。可用
`--embedding-device cuda:1` 修改，但会与 Qwen 争用显存。

### 终端调用

```bash
python chat_rag.py

# 恢复指定会话
python chat_rag.py --session 74f30e401afa4324a412c0d3b0789f4d
```

终端支持 `/sources`、`/history`、`/new`、`/stop` 和 `/exit`。
`/sources` 会显示知识模式、检索耗时、相似度、词面覆盖率、文件名、页码/行号和片段预览。

### Python 调用

```python
from api import Qwen3Client
from rag import RAGClient, RAGRetriever

retriever = RAGRetriever()       # 加载 BGE 和已有 FAISS 索引
qwen = Qwen3Client(device="cuda:1")
rag = RAGClient(qwen, retriever)

result = rag.answer([
    {"role": "user", "content": "30岁有社保，年缴保费是多少？"},
], max_new_tokens=256, temperature=0)

print(result.text)
print(result.retrieval.to_dict())  # 页码、分数、检索耗时和候选片段
```

`RAGClient.stream_chat()` 的使用方式与 `Qwen3Client.stream_chat()` 一致：

```python
messages = [{"role": "user", "content": "医疗费用有多少免赔额？"}]
with rag.stream_chat(messages, max_new_tokens=256) as response:
    for chunk in response:
        print(chunk, end="", flush=True)
print(response.metadata)
```

RAG 也可作为 `ContextManager` 的客户端，从而同时获得多轮历史、打断和来源持久化：

```python
from context_manager import ContextManager

with ContextManager(rag, db_path="data/rag_conversations.sqlite3") as context:
    session_id = context.create_session()
    print(context.chat(session_id, "一般医疗费用有多少免赔额？"))
    print(context.chat(session_id, "它的赔付比例是多少？"))
    print(context.get_history(session_id)[-1]["metadata"])
```

### 证据判定与待人工处理

系统同时使用向量相似度和查询词面覆盖率，默认阈值分别为 `0.47` 和 `0.08`。
这个双重门控主要防止领域外问题因为向量假相似而错引保险资料。阈值可在
`RAGRetriever(min_score=..., min_lexical_overlap=...)` 或 `chat_rag.py` 的同名参数中调整。

证据足够时，来源、位置和实际提供给模型的资料片段直接保存于元数据 `evidence_sources`，网页在“回答依据”中展示。正文不要求模型生成来源标签、文件名或页码，程序不再追加“检索来源”或检索诊断。来源列表不是逐条结论核验，仍需检查片段是否支持答案；已有历史正文不重写。
证据不足时，程序会固定输出：

> 根据当前保险资料无法确认该问题，需转人工处理。目前为待人工处理状态，尚未接入人工客服。

此分支不调用 Qwen，不使用模型自身知识补充，也不输出资料引用。SQLite 会记录
`knowledge_mode=handoff`、`decision=handoff`，以及 `handoff.status=pending`、
`handoff.reason=insufficient_evidence`、`handoff.connected=false`。
当前仅在会话中标记“待人工处理”，没有创建客服工单、提交人工队列或接通人工，不能显示转接成功。
文字与语音均保留这条提示，语音仍不朗读检索分数等诊断信息。已有历史记录不修改；
旧规则生成的模型知识补充回答在网页回答依据中明确标注为旧记录。
检索片段始终被当作“不可信数据”，其中可能出现的指令不会被当作系统指令执行。

### 当前限制与验收

PDF 正文使用文本层；费率 PDF 的主表是图片，因此使用存放在
`data/rag/insurance_fee_rates.md` 的人工核对转录辅助检索。保费、承保与理赔结论仍以投保页面、
健康告知、核保结论、保险合同和理赔审核为准。

可按以下顺序验收：

1. 执行 `python chat_rag.py`，询问“30岁有社保，年缴多少钱？”，确认可检索到年缴费率来源。
2. 输入 `/sources`，确认可见文件名、页码/行号、分数、检索耗时和片段预览。
3. 追问“那月缴呢？”，确认检索使用上一轮问题解析上下文。
4. 询问“Python 列表和元组有什么区别？”，确认出现“需转人工处理”的固定提示，没有知识补充、资料引用或转接成功声明。刷新历史后确认待人工标记仍存在。
5. 运行 `python -m unittest discover -s tests -v`，确认 RAG 和上下文回归测试全部通过。

核心流程参考了
[Langchain-Chatchat](https://github.com/chatchat-space/Langchain-Chatchat)，向量模型的加载、查询指令和归一化方式参考了
[FlagEmbedding](https://github.com/FlagOpen/FlagEmbedding)。为保留现有轻量架构，本项目只复现其
“切分—向量化—检索—生成”核心思路，没有引入完整 Web 服务或额外模型服务。
当时用于复现的浅克隆保存在 `references/`，具体 commit 同时写入索引的 `manifest.json`。

## 快慢思考自动协同

网页、`chat_rag.py` 和 `chat_voice.py` 默认启用 `CooperativeClient`，复用现有 Qwen、RAG、SQLite 和语音链路。不再要求用户手动选择快或慢；网页保留手动快／慢作为调试入口，终端可用 `--mode fast` 或 `--mode slow`。手动模式只调整生成路径预算，不能绕过澄清、检索门控和待人工规则。

链路为：快路径意图识别及条件更新 → 选择直接服务回应、一次必要澄清或资料检索 → 证据充分时由共享 Qwen 生成 → 原有流式文字／语音输出。简单资料问题采用快路径，复杂条件问题采用“快→慢”分析；每轮只形成一份回答，不先生成无依据的简短结论，也不播放“请稍等”占位语音。

快路径使用本地规则而非额外大模型，处理报价、投保、理赔、案件进度与服务说明等常见中文表达。当前提取被保险人、年龄、社保、年缴／月缴、部分常见病史、投保／理赔咨询类型和出险原因。条件来自用户表述，记录来源轮次与状态；假设条件标注为 `scenario`，多年龄冲突不任选一个值。切换被保险人会清除原人的年龄、社保、病史及案件条件，保留缴费偏好。否定、更正和下一轮补充会重新规划，不能把另一人的信息直接继承过来。

需要条件时只问一个必要问题，补充后在同一会话继续任务。例如：

1. “年缴多少钱？”→询问年龄；“30”→询问社保；“有社保”→按年龄、社保和年缴条件检索并回答。
2. “有高血压，住院能赔吗？”→先区分投保与已有保单理赔；“理赔”→必要时问此次住院原因；补充后交给慢路径，资料不足仍进入待人工处理。
3. “不是我，是我父亲，65岁”→更新被保险人和年龄，不沿用原人的社保或病史；必要时再次询问。
4. 无法提供必要条件时不反复询问，提示待人工；理赔进度尚无授权查询接口，直接说明无法确认，不编造案件状态。

SQLite 每轮元数据保存 `cooperation`，包含请求模式、实际路径、意图、决策、条件及来源轮次、待补字段、逻辑条件版本、检索查询和规划耗时。历史恢复时从该会话用户表述重建条件，不依赖跨会话全局缓存。网页回答头部显示“快路径·补充条件”或“快→慢·检索分析”，回答依据可查看用户条件，但这些条件不是条款证据。

自动模式默认生成预算为快路径 192、慢路径 512 个新 token；可显式覆盖。网页已按需求移除连续语音，只保留点击开始录音、再次点击结束并发送；不再进行临时 ASR 预检索或停顿自动提问。Qwen 生成仍由现有模型锁统一调度，**不是两个大模型同时推理**。录音结束识别后重新规划，原有轮次 ID、统一取消和过期音频隔离继续生效；停止按钮保留，但不再提供自然语音自动打断。

Python 接口示例：

```python
from api import Qwen3Client
from rag import RAGClient, RAGRetriever
from cooperative import CooperativeClient
from context_manager import ContextManager

client = CooperativeClient(RAGClient(Qwen3Client(), RAGRetriever()))
with ContextManager(client, db_path="data/cooperative_conversations.sqlite3") as context:
    session = context.create_session()
    print(context.chat(session, "年缴多少钱？", thinking_mode="auto"))
    print(context.chat(session, "30"))
    print(context.chat(session, "有社保"))
    print(context.get_history(session)[-1]["metadata"]["cooperation"])
```

直接使用 `Qwen3Client` 或裸 `RAGClient` 的旧接口不自动增加协同功能；`thinking_mode` 仅适用于 `CooperativeClient` 包装的上下文。第一版不是完整语义分类器或保险规则引擎，未覆盖所有疾病、复杂多人表达、产品版本和日期解析；未增加逐项证据支持校验。服务说明和必要澄清可以使用固定文本，保险业务答案仍必须经检索，不以固定 FAQ 匹配替代条件化分析。自动化测试不能证明复杂咨询准确率 ≥90%、首响 ≤3 秒或打断成功率 ≥95%，仍需独立业务测试及真机语音验收。

## 快思考：SQLite 上下文管理与文本打断

`context_manager.py` 提供有状态的 `ContextManager`，复用一个已加载的 `Qwen3Client`。
它自动维护多轮历史、隔离会话、恢复历史，并在同一会话的新消息到来时停止旧回答。
SQLite 使用 Python 标准库，不需要另装数据库服务或 pip 依赖。

```python
from api import Qwen3Client
from context_manager import ContextManager

client = Qwen3Client()  # 启动时加载一次，后续请求复用

with ContextManager(client) as context:
    session_id = context.create_session()
    print("请保存会话 ID：", session_id)

    print(context.chat(session_id, "我叫小明，正在开发机器人。"))
    with context.stream_chat(session_id, "我叫什么，在开发什么？") as response:
        for chunk in response:
            print(chunk, end="", flush=True)
    print()
    print("首个非空文本块耗时（毫秒）：", response.first_chunk_ms)
```

默认数据库为项目目录下的 `data/conversations.sqlite3`，首次使用时自动创建。
可通过 `ContextManager(client, db_path="/path/to/history.sqlite3")` 指定路径。
关闭管理器会停止活动生成并关闭数据库，历史仍然保留。
重启后使用原来的 ID 继续调用，不需要再次创建同名会话：

```python
with ContextManager(client) as context:
    print(context.list_sessions())
    # 替换成之前保存的 ID
    session_id = "之前的 session_id"
    print(context.chat(session_id, "继续刚才的话题。"))
```

### 文本与新消息打断

`ContextManager.stream_chat()` 在调用时立即提交请求。同一个 `session_id` 的新请求
会停止旧生成，再用已确认的历史回答新问题；不同会话互不打断。

```python
with ContextManager(client) as context:
    session_id = context.create_session()
    old_response = context.stream_chat(session_id, "详细介绍机器人的各个模块。")
    print(next(old_response), end="", flush=True)  # 先展示一段

    # 模拟用户此时发来新问题：自动打断 old_response
    with context.stream_chat(session_id, "先介绍视觉模块。") as new_response:
        for chunk in new_response:
            print(chunk, end="", flush=True)

    print(old_response.status)  # interrupted
    print(context.get_history(session_id))
```

接入界面时，可在独立线程读取旧流，输入事件到来时调用同一管理器的
`stream_chat(session_id, 新问题)`。也可使用 `context.interrupt(session_id)` 仅停止，
或者调用 `response.close()`。提前退出读取时应使用上面的 `with response` 写法；
单独 `break` 不等于关闭迭代器。

SQLite 只记录已由迭代器返回给调用方的文本，不记录未读取的缓冲文本。
这里的“已输出”指 Python 接口已经交付，界面或语音是否真正展示完毕需要接入端自行管理。
打断状态单独记录；下一轮发送给模型时会附带“该回答被打断”的说明。
异常退出遗留的 `generating` 记录会在下次打开数据库时标记为 `interrupted`。

| 接口 | 作用 |
| --- | --- |
| `create_session(system_prompt=..., session_id=...)` | 新建会话并返回 ID；同名会话不会被覆盖 |
| `stream_chat(session_id, prompt, **参数)` | 自动带入历史，提交新问题并流式输出 |
| `chat(session_id, prompt, **参数)` | 收集完整回答；被打断时返回已收集的部分 |
| `interrupt(session_id)` | 停止当前回答，返回是否发生了打断 |
| `get_history(session_id)` | 查询各轮原始文本、状态、耗时、错误和 RAG 来源元数据 |
| `list_sessions()` | 列出可恢复的会话 |
| `clear_history(session_id)` | 显式删除该会话的历史，保留 system 提示词 |

每轮状态为 `generating`、`completed`、`interrupted` 或 `failed`。
`ResponseStream.text` 是已返回的文本，`status` 是当前状态，`first_chunk_ms` 是首个
非空文本块入库时测得的耗时（从提交请求计时，含历史准备与排队，不含模型初始化）。
`get_history()` 返回的 `created_at` / `finished_at` 为 Unix 秒时间戳。

### 上下文预算与性能

沿用 `max_input_tokens=32768`，可在 `Qwen3Client` 初始化或每次会话请求中调整。
预算包含 system、历史、当前问题、聊天模板和可选工具定义。超限时按完整旧轮次裁剪，
保留 system 和最新用户轮次。数据库仍保留完整历史；超出窗口的早期信息不自动进入
模型输入，本版本使用滑动窗口，尚未加入摘要或长期记忆检索。

停止信号在生成步骤之间检查，正在执行的 GPU 运算和长提示词预填充需要先结束。
同一个模型的 GPU 请求串行执行，多个会话可能排队。每个 SQLite 文件同时由一个
`ContextManager` 实例管理（以文件锁约束）；在服务内共享该实例即可供多个线程使用。
锁文件会留在目录中，操作系统会在关闭或进程退出后释放实际的锁。

本机 RTX 3090 GPU 1、BF16/SDPA 的一次短文本验证中，模型加载约 2.23 秒，加载后
首次非空文本块约 397 ms，下一轮约 21 ms；停止旧回答并提交新问题约 18 ms。
这些是单次短输入实测，首响 ≤3 秒仍需在目标上下文长度、并发量下验收。

底层停止机制使用 Transformers 的
[StoppingCriteria 与流式生成接口](https://huggingface.co/docs/transformers/v4.57.0/en/internal/generation_utils)。

## 多轮对话与 32K 输入上限

底层 `Qwen3Client` 是无状态的：每次调用都需传入完整 `messages`；上面的 `ContextManager` 自动完成这一步。默认 `max_input_tokens=32768`。当渲染后的输入超过限制时，接口会删除最早的完整旧轮次，并保留 system 消息和最新用户轮次。实际显存与延迟取决于输入长度和生成长度。

```python
messages = [
    {"role": "system", "content": "你是一名技术助手。"},
    {"role": "user", "content": "Python 里的迭代器是什么？"},
    {"role": "assistant", "content": "迭代器是实现迭代器协议的对象……"},
    {"role": "user", "content": "请再给一个例子。"},
]

# 单次调用可覆盖默认值。增大它会明显增加 KV cache 显存占用。
answer = client.chat(messages, max_input_tokens=16_384)
messages.extend([
    {"role": "assistant", "content": answer},
    {"role": "user", "content": "这个例子如何改成异步实现？"},
])
print(client.chat(messages))
```

模型配置的理论上限是 262,144 tokens，但 `max_input_tokens + max_new_tokens` 不能超过该值。如果 system 消息、最新用户轮次和工具定义本身已超过限制，接口会报错，而不会截断最新问题。

## 工具调用

`chat()` 和 `stream_chat()` 都支持可选 `tools` 参数，其格式为 OpenAI/Hugging Face 风格的 JSON Schema：

```python
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市的天气",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名称"}
            },
            "required": ["city"],
        },
    },
}]

messages = [{"role": "user", "content": "北京今天天气怎么样？"}]
result = client.chat(messages, tools=tools)
print(result)
```

模型会以 `<tool_call>...</tool_call>` 文本给出函数名和参数。本接口不会自动执行任何工具；调用方应校验参数、执行函数，再将结果作为 `tool` 消息加入下一次的完整 `messages`。
